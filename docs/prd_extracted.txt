82: 1. Executive Summary
83: ProMove Innovation Cloud is a student-centered innovation ecosystem built on the MERN stack, connecting Students, Schools, Colleges, Mentors, Investors, HR professionals, and Super Admins into one unified platform. The architectural spine is: Identity → Verification → Team / Project → Evidence (tickets, assets, outcomes) → Transactions (mentorship / pitch / hiring / sales). Every other role exists to support, evaluate, invest in, or hire from the student community.
84: The platform enforces three complementary authorization layers: RBAC for baseline role powers, Scoped Access for institution and contract boundaries, and State Guards for workflow-locked actions (e.g., a pitch deck may only be uploaded after a pitch is accepted). This three-layer model follows OWASP's recommendation that authorization must be server-side, default-deny, and centralized rather than scattered across route guards.
85: 1.1 Platform Vision
86: To create a connected innovation ecosystem where every participant adds measurable value to the student journey:
87: Students build real-world projects, compete, get mentored, pitch to investors, and get hired
88: Schools and Colleges maintain verified rosters, organize events and hackathons, and act as trusted gatekeepers for HR and investors
89: Mentors bid on project teams, manage SDLC workflows, and earn through an escrow payment system
90: Investors discover curated projects, manage pitch pipelines, and monitor funded team progress
91: HR professionals access verified talent pools via campus drives or direct outreach and run structured interview pipelines
92: Super Admins govern platform integrity, privacy, audit trails, and system configuration
93: 1.2 Authorization Philosophy (Three-Layer Model)

212: 2.4 Three-Layer Authorization Middleware
213: Every API request passes through a three-stage pipeline before reaching the route handler:
214: Authenticate: Verify JWT signature (RS256), decode payload {userId, role, institutionId, contractIds[]}
215: Role-Check: Match requested action against role permission set from centralized permission config
216: Scope + State Guard: Verify resource ownership and that the workflow state permits this action
217: OWASP Transaction Authorization: Authorization must be enforced server-side. Transaction state (e.g., pitch accepted, contract active) must be checked at every protected action — not assumed from client-side state.
218: 2.5 Authentication Token Strategy
219: Following RFC 7519 and OWASP Session Management guidance:
220: Access Token: JWT signed with RS256, 15-minute TTL, carried in Authorization header
221: Refresh Token: Opaque token, 7-day TTL, stored in HttpOnly + Secure + SameSite=Strict cookie
222: CSRF Defense: Cookie-to-header CSRF token pattern for all state-mutating endpoints
223: Password hashing: Argon2id (preferred) with fallback to bcrypt (12 salt rounds) per OWASP Password Storage Cheat Sheet
224: Token rotation: Refresh tokens rotated on every use; old token invalidated immediately

366: 4. Role-Based Dashboards & Feature Specifications
367: Role 1 — Student Dashboard
368: Students are the platform's core users. Every feature, every other role, and every data flow ultimately serves the student's innovation, learning, and career journey. The student dashboard is the most feature-rich module and acts as the heartbeat of the application.
369: Identity Foundation: A student's profile becomes fully trusted only after institution verification. Verified status unlocks: institution leaderboard, HR visibility, event eligibility, and investor discovery. Unverified students have a limited but functional sandbox.
370: 4.1 Student Identity & Verification
371: Register with email + password (Argon2id hashed)
372: Email verification link sent on registration
373: Link to School or College via: institution invite code, institutional email domain match, or manual verification request
374: School/College admin approves roster match → student receives Verified Institution Badge
375: Verification unlocks: institution leaderboard, HR visibility, hackathon eligibility, verified portfolio badge
376: Unverified students can still create projects, use Jira boards, and list in marketplace
377: Institution verification is non-blocking for core features but required for hiring/investment visibility
378: 4.2 Project Management — Jira-Style Board
379: Create a project: title, description, tech stack, domain tags, team visibility setting
380: Team management: invite by email or student ID; assign roles (Lead, Developer, Designer, Tester, DevOps)

382: Tickets/Issues: title, description, priority (P0 Critical → P3 Low), assignee, due date, labels, attachments
383: Epics and Milestones: group tickets under epics; milestones trigger mentor approval and investor notifications
384: Sprint Planning: create sprints (1–4 weeks), assign backlog tickets, set sprint goal and acceptance criteria

1002: 9. Security Architecture & Compliance
1003: OWASP Top 10 (2025): Broken Access Control remains the #1 vulnerability class. Every design decision in this section is grounded in OWASP, NIST, and RFC standards.
1004: 9.1 Authentication Security
1005: Password hashing: Argon2id (primary, per OWASP Password Storage Cheat Sheet); bcrypt (12 rounds) as fallback
1006: JWT (RFC 7519): RS256 signed, 15-minute access token TTL; opaque refresh token with 7-day TTL
1007: Refresh token storage: HttpOnly + Secure + SameSite=Strict cookie — inaccessible to JavaScript
1008: CSRF defense: Double-submit cookie pattern for all state-mutating requests
1009: Token rotation: every refresh token use invalidates the old token (sliding window)
1010: Brute-force protection: rate limit login endpoint (5 attempts per 15 minutes per IP)
1011: Optional 2FA: TOTP authenticator app for high-privilege accounts (Mentors, Investors, Admins)
1012: 9.2 Authorization Security
1013: Default-deny: all routes return 403 unless explicitly permitted by RBAC middleware
1014: Server-side enforcement: authorization decisions never delegated to client-side state
1015: Scope checks: resource ownership verified at handler level (not just route level)
1016: State guards: workflow-locked actions verified against document state in DB before execution
1017: Audit trail: all sensitive actions logged with actorId, role, action, resource, IP, timestamp
1018: 9.3 File Upload Security (OWASP File Upload Cheat Sheet)
1019: Allowed extensions whitelist: .pdf, .docx, .pptx, .png, .jpg, .zip, .md only
1020: MIME type validation: check both Content-Type header AND file magic bytes (file signature)
1021: Filename sanitization: strip path traversal characters, normalize to UUID-based S3 key
1022: Size limits: enforced server-side before presigned URL issuance (not just client-side)
1023: Storage isolation: uploaded files stored in S3 with no public access; only presigned URL access
1024: Presigned URL guardrails (AWS guidance): time-limited (15 min for upload, 1 hour for download), scoped to specific S3 key
1025: Virus scan: optional ClamAV integration on S3 trigger for high-risk file types (ZIP, DOCX)
1026: 9.4 Application Security
1027: Helmet.js: sets Content-Security-Policy, HSTS, X-Frame-Options, X-Content-Type-Options headers
1028: CORS: explicit origin whitelist — no wildcard in production
1029: Input validation: Joi schemas on all request bodies; express-validator on query params
1030: MongoDB injection: Mongoose automatic query sanitization; avoid raw $where operators
1031: Rate limiting: express-rate-limit per role and per endpoint type
1032: Dependency audit: npm audit in CI/CD pipeline; Dependabot for automated security updates
1033: 9.5 Privacy & GDPR Compliance
1034: Data minimization: only collect fields explicitly needed per role
1035: Student data visibility to HR: scoped to name, skills, leaderboard, portfolio — never raw grades without college opt-in
1036: Direct hire visibility: student must explicitly opt-in; default is private
1037: Right to erasure: /DELETE /api/v1/users/me cascades deletion across all collections; logged to audit trail
1038: Data retention: define retention policies per data type (audit logs: 2 years, session tokens: 7 days, files: user-controlled)
1039: Super Admin data purge: GDPR-compliant purge endpoint with 2-admin confirmation for irreversible actions
